Claude Code に長期記憶を持たせる自作ツール kita-memory を運用しています。中の仕組みは別記事に書きました（[Claude Code に長期記憶を持たせる自作ツール kita-memory の仕組み](https://zenn.dev/kitamotors/articles/2026-05-13-kita-memory-architecture-overview)）。今回はその運用で、また Gemini の無料枠に詰まった話です。前に詰まったのは「保存」側でしたが、今回は「要約」側でした。

## 何が起きていたか

ある日 Supabase の中を見たら、要約待ちのデータ（`raw`）が 59 件、失敗扱い（`failed`）が 11 件たまっていました。保存自体は動いています。でも夜間に走るはずの要約バッチが、入ってくる量に追いついていませんでした。

## 原因

kita-memory は、貯めた会話ログを Gemini に渡してセッション単位の要約に変換しています。詰まっていたのはこの要約でした。

効いていた上限は、embedding 側の枠ではなく、要約モデルの「1 日あたりのリクエスト回数」でした。無料枠だと実測でだいたい 20 回程度。しかも `gemini-2.5-flash` と `gemini-2.5-flash-lite` が同じ枠を共有していて、モデルを変えても増えませんでした。

設計が「1 セッション＝要約 1 リクエスト」だったので、1 日に作られる会話セッションが 20 を超え続けると、要約は永久に追いつきません。これは一時的な不調ではなく、構造の問題でした。

## やったこと

お金を払って枠を上げる手もありましたが、無料のまま使い続けたかったので、コード側を直すことにしました。

複数のセッションを 1 回のリクエストにまとめて投げる「バッチ要約」にしました。プロンプトの中で `=== SESSION <id> ===` という見出しで区切り、結果も session_id ごとに返してもらって振り分けます。1 リクエストに 10 件前後まとめれば、同じ 20 回の枠でも 10 倍近く回せます。

検証では、4 セッションが 1 リクエストにまとまって処理されるのをログで確認しました。滞っていたぶんも消化され、要約済みは 487 件から 574 件になり、`raw` と `failed` は 0 になりました。

1 件の壊れたセッションがバッチ全体を巻き込まないように、極端に大きいセッションは単独で処理し、バッチが失敗したときは従来の 1 件ずつの方式に自動で戻すようにしています。

## 詰まりどころ

**`failed` の半分は無実でした。** 失敗扱いにしていたデータを調べたら、本当に壊れていたのではなく、クォータ切れ（429）の巻き添えで failed にされていただけでした。エラーの種類で分けて、一時的なものは据え置き、本当に壊れたものだけ failed にするよう直しました。failed を戻して再実行したら、ほとんど回収できました。

**デプロイで転びました。** 要約は Supabase の Edge Function でも動いていて、毎日決まった時刻に呼ばれます。これを更新するとき、コマンドのフラグがコピペの改行で 2 行に割れて、JWT 検証が ON に戻ってしまいました。その状態だと定期実行が 401 で弾かれます。直そうと自作したバッチファイル（`.cmd`）も、改行コードのせいで Windows に「構文が正しくありません」と怒られました。最終的にデプロイ手順をスクリプトに固定して落ち着きました。

## まとめ

保存側を無料枠から守っても、要約側にもっと小さい別の枠が残っていました。処理の単位を「1 件ずつ」から「まとめて」に変えるまで、構造的に詰まったままだったという話です。同じように無料枠で何かを回している人は、回数のほうも数えておくと早めに気づけると思います。
