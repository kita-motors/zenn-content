Claude Code は便利ですが、セッションをまたぐと前のやりとりを覚えていません。同じ説明を毎回繰り返すのに地味に時間を取られていたので、過去の壁打ちと業務メモを Claude Code 自身に引かせるための仕組みを、この春から作り始めました。`kita-memory` という個人プロジェクトです。

書き始める前に断っておくと、私は事務・管理部門に所属している非エンジニアで、プログラミングは Claude Code と一緒に書いている人間です。なので技術的な細部に深入りする記事ではなく、**「なぜ作ろうと思ったか」「どう判断したか」「実際に何が変わったか」** が中心の話になります。コードを動かす部分は、ほぼ Claude Code に書いてもらいました。

## なぜ作ろうと思ったか

私の業務では、社内ツールの改修や API 連携のトラブルシュートを Claude Code と壁打ちしながら進めることが多いのですが、セッションを閉じるたびに「先週これで決着がついた」「あのプロジェクトでこの API はこう叩いた」といった文脈が消えていきます。

具体的に困っていたのは、

- 数日前に出した結論を、別セッションで Claude Code に聞き直すと「もう一度考えてみましょう」と振り出しに戻る
- プロジェクトを切り替えると、過去のハマり所が引き継がれない
- そのたびに自分で過去のメモを探しに行く必要がある

つまり、**Claude Code 側に「思い出させる仕組み」が欲しい**、という素朴な動機です。

## 先人の設計を参考にさせてもらう

「同じことを考えている人はいないか」とまず探したら、noprogllama さんの記事に出会いました。

[Claude Code に長期記憶を持たせたら、壁打ちの質が変わった](https://zenn.dev/noprogllama/articles/7c24b2c2410213)

ここで紹介されている **sui-memory** は、まさに私が欲しかったもののプロトタイプという感じで、

- セッション終了時に会話を自動で保存する
- ベクトル検索だけでなくキーワード検索も併用する（ハイブリッド）
- 古い記憶は時間で減衰させる

といった設計の骨格がすでにありました。記事を読んで「これに乗っかれば自分も作れる」という見通しが立ち、kita-memory はこの設計を出発点にしています。先に深く検証された方の肩を借りる形になりました。ありがとうございます。

### でも、自分の手に馴染むスタックに変えたかった

参考元の sui-memory は Python + SQLite で完結している、依存のミニマルな構成です。ただ私の場合、

- 普段業務で書いているコードがほぼ TypeScript なので、自分でメンテできる言語に揃えたかった
- 別マシンからも触りたかったので、ローカル DB よりはマネージドな Supabase に置きたかった
- すでに業務で Gemini を使っており、追加の API は増やしたくなかった
- そして何より、Claude Code から **MCP サーバー経由で呼び出させる** という形にしたかった

という都合があり、技術選択はガラッと変えています。設計思想は借りて、道具は手元のものに置き換えた、という関係です。

## ざっくりした全体像

中身を全部説明すると長くなるので、図だけ。

```
[Claude Code セッション]
   │
   ├── hook ─→ 会話を自動で保存 ──┐
   │                              ▼
   │                          ┌─────────────┐
   │                          │  Supabase   │  ← 会話ペアと埋め込みを蓄積
   │                          │  (pgvector) │
   │                          └──────┬──────┘
   │                                 │
   └── MCP サーバー ←── Claude Code が必要なときに検索
```

ポイントは2つだけです。

- **保存は自動で裏でやる**（Claude Code の hook 機能で、セッション終了時に会話を読んで保存する）
- **検索は Claude Code に任せる**（MCP サーバーとしてツールを公開しておくと、必要なときに Claude Code 自身が呼んでくれる）

「人間が手を動かさなくても勝手に貯まり、Claude Code が自分で取り出せる」という状態に持っていけたら勝ち、という設計です。

## 作っていて非エンジニアとして詰まったところ

ここが、AI で量産される記事には出てこない部分だと思うので、思い出せる範囲で正直に書きます。コードに詰まったというより、**概念や判断のところで止まる** ことが多かったです。

### MCP の概念が多層で頭に入らない

公式ドキュメントを読むと、Server / Client / Transport / Tool / Resource / Prompt と言葉がたくさん出てきます。「全部分かってから書き始めなきゃ」と思うと完全に止まります。

結局、Claude Code と相談しながら **「とりあえず Tool だけで始めよう」** という割り切りに落ち着きました。Resource や Prompt は使わなくても、検索ツールを1〜2個登録するだけで形になります。最低限のところから始めて、必要になったら覚える、という非エンジニア式の進め方で何とかなりました。

### hook と MCP のどっちで何をやるか

Claude Code には hook（特定のタイミングで自動的に何かを実行する仕組み）と MCP（Claude Code が呼べるツールを外から提供する仕組み）の両方があります。最初「同じようなことができそうなのに何が違うの？」と混乱しました。

最終的に納得した役割分担は、

- **書き込み（保存）は hook 側**: 人間も Claude Code も意識しなくても、勝手に貯まっていてほしいから
- **読み込み（検索）は MCP 側**: 「今この文脈なら過去を見るべき」を Claude Code に判断してほしいから

これは Claude Code に「どう設計するのが自然？」と聞きながら詰めた部分です。一人だと迷子になっていたと思います。

### Supabase の権限設定で長く止まった

Supabase は標準で「全部禁止、必要な操作だけ明示的に許可する」という設計（RLS と呼ばれる仕組み）になっています。個人利用なので最初は全部許可で動かしていたのですが、「もし API キーが漏れたら全部やられるよな」と気になり始め、

- 読み込みと書き込みだけ許可する
- 更新と削除は禁止する（管理操作は別の権限の強いキーで）

という形に締めました。エンジニアの人なら「そりゃそうだよね」で済む話だと思うのですが、私は「どこまで締めると自分が困らないか」の感覚がなくて、ここで結構考え込みました。

### `.env` が読まれない・MCP が認識されない、みたいな初歩のつまずき

最初、MCP サーバーを起動しても接続先の情報が undefined になっていました。原因は環境変数を書いた `.env` ファイルの置き場所と、サーバーが起動する作業ディレクトリがズレていたからです。

似たような「設定したのに反応しない」系のつまずきは何回かあって、その都度 Claude Code に「これ動かないんだけど」とログを貼ると原因を切り分けてくれる、という流れでした。詰まる場所自体は他の人と同じだと思うのですが、**自力で原因を特定する前に AI に聞いてしまう** のが私の進め方です。

## 何が変わったか

ここが一番伝えたい部分です。仕組み自体は派手ではないのですが、業務での効き方が想像以上でした。

- **プロジェクト横断で過去の判断が引き出せる**: 「あのとき API のスコープどうしたっけ」を Claude Code が自分で記憶を検索して思い出してくれる
- **「昨日何やったっけ」が消える**: 直近の会話履歴を Claude Code 側で取れるので、朝イチの立ち上がりが速くなった
- **壁打ちが「線」になる**: 単発の問答ではなく、過去の文脈と地続きで Claude Code が応答するようになる

副次的な効果として、**自分自身もこれを業務日誌として使える** ようになりました。Claude Code に「先週この件どうやって解決したっけ」と聞くと、私が当時書いた質問と Claude Code の応答がそのまま出てくる、という体験はかなり気持ちがいいです。

## まとめ

- セッションをまたいで Claude Code に過去を思い出させる仕組みは、先人がすでに大枠を作ってくれていた
- 設計思想は借りて、道具は自分の手に馴染むものに置き換えた
- 非エンジニアでも、概念を全部覚える前に「最小限から動かす」ができれば形になる
- 効くのは技術より、**「文脈が積み上がる」という状態そのもの**

この春に作り始めたばかりなので、しばらく自分で使い倒しながら、運用で気になった部分を直していくつもりです。
